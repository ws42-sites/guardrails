# Guardrails 0.7.0 plan: closing the verification-stack gaps

Status: in progress on branch `verification-stack-gaps` (one draft PR). Nothing here is merged, tagged or published.

## Versioning
- Target **0.7.0**, not 0.6.2: 0.6.3 is already on npm, and this release adds features and config keys (a minor bump under 0.x).
- **1.0** means Guardrails is used in production by third parties (outside ws42), with a stable config and CLI.
- **2.0** means a breaking redesign (config format or rule IDs change incompatibly).
- Every new feature in 0.7.0 is off by default. A basic install stays zero-config and behaves exactly like 0.6.3.

## Source
The "Top 7 Verification Stack" distilled from seven AI Engineer talks. Guardrails already covers 1 (deterministic rules), 2 (fast pre-merge checks) and 4 (anti-gaming). This release closes 5, 6 and 7 and lowers the CI burden of the whole stack.

## Workstreams

### W1. Independent reviewer (gap 5), `src/review/**`, specs REVIEW-01/02, rule REVIEW-1
- `guardrails review` and `guardrails check --review` run after Guardrails' own checks.
- Input is only the merge-base diff and the test output (the guardrails report). Never the author's reasoning, PR description, commit messages, branch name or author.
- Typed `Reviewer` provider interface: `stub` (deterministic, regex `failOn` over added lines, used in tests and CI) and `command` (spawns a configured command, JSON in on stdin, JSON verdict out; runs in an empty temp dir with a scrubbed env; fails closed on timeout, non-zero exit or a malformed verdict).
- Verdict `pass | fail` with findings `{file, line?, message}`. A fail becomes REVIEW-1 findings.
- No model calls in tests or CI. Real model spend needs Josh's OK, so `review.enabled` defaults to false.
- Reviewer prompt (for `command` providers that wrap a model) is short: intent plus constraint.

### W2. Commit-pinned provenance (gap 6), `src/provenance.ts`, specs PROV-01/02, rule PROV-1
- `guardrails provenance record` writes `guardrails-provenance.json`: tested SHA, merge parents, PR head SHA, report path and sha256, guardrails version, checks run with results, override labels with who and why.
- The same record goes into the job summary (and optionally a PR comment) as `<!-- guardrails:provenance v1 <base64url json> -->`, and into a 90-day artifact, so force-pushes and expiring logs don't erase it.
- `guardrails provenance verify --head <sha>` fails PROV-1 unless the tested SHA is the head, or a merge commit whose second parent is the head; a changed report hash also fails.
- Off by default (`provenance.enabled`).

### W3. Weekly checker evaluation (gap 7), `src/evaluate.ts`, specs EVAL-01/02
- Ledger `.guardrails/ledger.jsonl` (locked like the rest of `.guardrails/`): `escaped-bug` (a merged PR that passed, later linked to an issue labelled `guardrails:escaped-bug`) and `false-escalation` (a block later overridden by an approval label).
- `guardrails ledger add|import` validate and dedupe; import reads GitHub event exports, so the CLI makes no network calls.
- `guardrails evaluate --since 7d` diffs the ledger against the rule set and proposes prunes (rules with repeated false escalations) and sharpening (escaped bugs, by rule or unattributed). Report only, never applied.
- Example weekly workflow posts the report to the job summary and, if enabled, as a draft PR or issue for a human.

### W4. `guardrails.md` config format, `src/config-md.ts`, specs CFGMD-01/02
See "guardrails.md format" below. Parses into the same typed config as `guardrails.config.json`, is locked by the agent hooks, and counts toward the TEST-7 weakening check.

### W5. Label planner (first CI job), `src/label-planner.ts`, specs LPLAN-01/02
- `guardrails labels plan --base <ref>` (`src/label-planner.ts`) statically scans the diff and lists every approval label the PR will need, with the reason and `file:line`: `guardrails:existing-behaviour-tests-approved` (new tests whose product files did not change), `guardrails:config-approved` (config loosened), `guardrails:tests-removed-approved`, `guardrails:baseline-approved`, `guardrails:journeys-approved`, `guardrails:flags-approved`.
- Runs as the first job and writes one markdown summary (and optionally one PR comment), so a human adds every label in one round trip instead of fail, label, rerun.
- Advisory only: always exits 0 and never adds labels.

### W6. Feedback loop, `src/feedback.ts`, specs FEED-01/02
- Every blocking finding is tagged `{rule, file, agent}` (agent from `GUARDRAILS_AGENT_NAME`, else the PR author) and appended to a failure log artifact.
- The weekly job clusters repeats (same rule and normalized message, at least N times) and drafts a candidate lint rule (a `restrictedStrings` or ESLint `no-restricted-syntax` entry) with a one-line rationale, opened as a draft PR for human approval. Never auto-merged.

### W7. Public npm readiness, `src/telemetry.ts`, specs TELEM-01/02
- Five-minute quickstart in the README.
- Opt-in anonymized telemetry on `init` and on each `check`: off unless opted in (`telemetry.enabled` plus an endpoint), disabled by `GUARDRAILS_TELEMETRY=0` or in `guardrails.md`. No PII. The payload is documented: version, node major, OS family, command, rule counts, duration and a random install ID. No npm postinstall hook, and no network in tests (injected fetch).
- Public changelog (`CHANGELOG.md`, Unreleased section) and a README CI badge showing Guardrails passing on itself.

### W8. CI burden optimizations
- The reviewer is triggered only on PRs that touch locked tests (spec-tagged tests, `.guardrails/`, config) or auth paths (`review.paths`). Otherwise it is skipped with a reason.
- The reviewer shards by file (`--shard i/n`) and runs as its own job in parallel with the test shards.
- Provenance writes are batched (one record per run, not per check) and async fire-and-forget: the SHA binding is computed synchronously at check time, and only the artifact or comment upload is deferred. A failed upload never turns a fail into a pass, and `verify` still fails closed.
- The weekly evaluator caches results keyed by the ledger hash, rules hash and window.
- Full-repo mutation moves from every push to main to the nightly schedule. Pushes to main run mutation on the changed files only (incremental), and nightly still runs everything.

### W9. Prompts
All prompts (reviewer, rule drafting, agent briefs) state the intent and the constraint in a few lines and trust the model.

## guardrails.md format
`guardrails.md` sits next to `AGENTS.md`/`CLAUDE.md`. Prose is for people and agents. Config lives in two places:

1. Optional front matter: flat `dotted.key: value` lines (booleans, numbers, quoted or bare strings, inline JSON arrays or objects). `#` lines are ignored.
2. Fenced blocks with the info string `guardrails` or `json guardrails`, each holding one JSON object.

````markdown
---
review.enabled: true
review.provider: stub
provenance.enabled: true
evaluation.windowDays: 14
telemetry.enabled: false
---
# Guardrails

Agents: never edit spec-tagged tests; flag conflicts instead.

```json guardrails
{ "rules": { "DOC-1": "warn" }, "mutation": { "break": 75 } }
```
````

Precedence (lowest to highest): built-in defaults, then guardrails.md fenced blocks (in document order, objects deep-merged, arrays and scalars replaced), then guardrails.md front matter, then `guardrails.config.json`. The JSON file wins on conflicts, so adding a `guardrails.md` never changes an existing install. Either file alone is enough. `version` defaults to 1. `journeys` and `deps` stay in the JSON file (their approval flows write it), and the parser rejects them in `guardrails.md` with a line number.

## CI weight
A 0 to 100 score of how heavy CI is per change and per day (lower is better). Target: under 40.

```
weight = 25*min(1, P/10) + 25*min(1, J/30) + 25*min(1, M/120) + 25*min(1, N/120)
```
- P = PR critical path: wall minutes of the longest PR job.
- J = total job minutes for one PR run.
- M = total job minutes for one push to main.
- N = total job minutes for one nightly run.

Measured with `node scripts/ci-weight.mjs <prRunId> <mainRunId> [nightlyRunId]` from `gh api` job timings (when no nightly run exists yet, the main run stands in for it).

Before, measured with the script (PR #20 run 44786756808, main push run 44787532457, main standing in for nightly): P = 1.3, J = 3.3, M = 127.7, N = 127.7, **weight 56**. Each push to main ran the unsharded full mutation run, which hit its 120-minute timeout and was cancelled, so it never even saved its incremental cache.

Levers built in this PR:
- Every guardrails job runs its check once. The `check` job used to run the whole check three times (`report --format json`, `report --format markdown`, `check`) and the mutation jobs twice. Now `check --format json` runs once and `report --report <file>` re-renders the saved JSON.
- Pushes to main mutation-test only the files changed since `github.event.before`. The full run is nightly and manual only.
- The nightly full mutation run is split into 4 shards (`mutation-shards` input), and each shard restores and always saves its own Stryker incremental cache. The first run pays full price; later runs only re-test changed mutants.
- The reviewer, provenance and label-planner jobs add under a minute each: the reviewer skips itself unless the change is risky, provenance is one batched write per run, and the label planner is a static scan.

After: see the PR body for the measured PR run. Main-push and nightly figures can only be measured after merge.

## Build
- Codex CLI on Josh's PC is the primary builder (agy as fallback), one instance per workstream in its own clone under `C:\dev`, each owning its own new files and a distinct anchor in `src/cli.ts`. They are combined on the box into this one branch.
- Every new module is in T1 (mutation-tested in CI, aim for 85% or more). No code comments. Tests are table-driven and fail on base. Baselines only shrink, and nothing uses `--force`, `--allow-increase` or skips checks.
- Workflows, README, CHANGELOG and integration are done on the box.

## Done when
- Dogfood CI (test, guardrails check, mutation, secrets) passes on the PR, apart from any approval label a code owner has to add, which the label planner lists up front.
- The mutation scores of gaming (99%), ci (97%) and mutation (99%) hold, and new modules are at 85% or higher.
- CI weight is under 40.
